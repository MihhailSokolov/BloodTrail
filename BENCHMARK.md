# Benchmark: BloodHound CE with and without BloodTrail

Every query BloodHound ships, plus a set written to attack the engine's weak
spots, run against the same graph on the same host -- once with the stock
PostgreSQL graph driver, once with BloodTrail.

## Setup

| | |
|---|---|
| Hardware | Apple MacBook Pro, M3 Pro; Docker Desktop VM given 12 CPU and 7.65 GiB |
| Images | both `linux/arm64`, native on the host |
| BloodHound CE | v9.7.0, same version both arms |
| Graph | 996,587 nodes / 2,435,479 edges, generated by [`bench/shgen`](bench/shgen) and ingested through BloodHound's own SharpHound upload pipeline |
| Composition | 450,008 Users, 220,000 Computers, 22,057 Groups, 4 Domains; 60,000 AZUsers, 20,000 AZDevices, 3,000 AZGroups, 601 AZApps, 20 AZRoles |
| Harness | [`bench/shgen/sweep.py`](bench/shgen/sweep.py), one discarded warm-up then the median of 3, 0.25s between calls, `include_properties: false` |
| Queries | 182 paired scenarios |

### How the arms were isolated

Three things have to hold for this comparison to mean anything, and an
earlier revision of this file got all three wrong.

**Both images must be native.** The stock `specterops/bloodhound` image is
`linux/arm64`; the BloodTrail image was being built `linux/amd64`, which Docker
on Apple Silicon runs under x86 emulation without complaint. The engine is
CPU-bound in a way BloodHound's HTTP layer is not, so emulation distorted it
far more than the stock arm: a full scan measured 775ms emulated against 122ms
native, and every BloodTrail number had to be discarded. Local image builds now
default to the Docker daemon's own platform. Both images here are `linux/arm64`.

**The other arm must be stopped entirely.** Each arm is its own Compose stack
with its own PostgreSQL and Neo4j. Stopping only the other arm's `bloodhound`
service leaves both databases resident, and in a 7.65 GiB VM that competition
lands on whichever arm is being measured.

**Settling has to be real.** BloodHound re-runs its post-ingest analysis on every
start, for about 105 seconds. The arm under test is force-recreated so the
`Finished Running Analysis Operations` marker in its log belongs to this run
rather than a previous container's, then left until compaction has been quiet
for 180s. Both databases were `VACUUM FULL`-ed first so neither was read from
a bloated state.

## Where BloodTrail is slower

58 of 182 scenarios show a higher number for BloodTrail, the worst by
1.47x. All of them are shipped prebuilts that both engines answer
in about 20ms, and the reason is the same for each.

Every request through `/api/v2/graphs/cypher` pays BloodHound's own pipeline --
parse, rewrite, complexity analysis, two emitter passes, response assembly --
before and after the graph is touched. BloodHound logs how long its read
transaction took and BloodTrail logs how long its engine took, so a request
splits three ways. Measured directly, 15 repetitions per query, one arm at a
time:

| Scenario | Arm | Wall | Graph transaction | Engine | BloodHound pipeline |
|---|---|---:|---:|---:|---:|
| Privileged Role Administrator | stock | 17.3 ms | 0.95 ms | — | 16.4 ms |
| Privileged Role Administrator | BloodTrail | 22.2 ms | 1.38 ms | 1.19 ms | 20.8 ms |
| Map domain trusts | stock | 19.1 ms | 2.26 ms | — | 16.8 ms |
| Map domain trusts | BloodTrail | 22.0 ms | **2.05 ms** | 1.84 ms | 20.0 ms |

The graph work is one to two milliseconds on either arm -- on `Map domain
trusts` BloodTrail's is the lower of the two -- and about 18ms of every such
request is BloodHound's pipeline, which neither driver influences. What is
left is a few milliseconds of general execution in a process holding a
gigabyte more, and on a query whose real work is a millisecond that is the
whole difference.

### Read the small rows carefully

At this scale the sweep's median-of-three is not a stable measurement. Taking
the 22 worst-looking rows and re-running them 15 times each, nine flipped to
faster, PostgreSQL's own timings moving the most:

| Scenario | Sweep | 15 repetitions |
|---|---:|---:|
| Workstations where Domain Users can RDP | 1.15x slower | **1.96x faster** |
| Domains with smart card accounts that do not expire | 1.17x slower | **1.92x faster** |
| Servers where Domain Users can RDP | 1.11x slower | **1.41x faster** |
| Computers where Domain Users can read LAPS passwords | 1.31x slower | **1.15x faster** |

So treat any ratio in the table below as indicative, not decisive, for
scenarios under roughly 25ms. The queries that take real time are not
affected by this: a 49-second query does not move by a few milliseconds.

## Reproducing

```bash
# Generate a hybrid AD + Entra forest as SharpHound collection JSON, then
# upload the zip through BloodHound's ordinary file-ingest UI or API.
go run ./bench/shgen -users 450000 -computers 220000 -groups 22000 \
    -domains 4 -az-users 60000 -az-devices 20000 \
    -out shgen-out -zip shgen.zip

# Build the BloodTrail image; a local build targets the host's own platform.
# Confirm BOTH arms: docker image inspect <image> --format '{{.Architecture}}'
./build/build-image.sh v9.7.0

# Sweep ONE arm at a time, with the other stack stopped ENTIRELY, and only
# after this run of BloodHound's analysis has reported it finished.
python3 bench/shgen/sweep.py --port 8080 --password "$PASS" \
    --label stock-pg --corpus bench/shgen --repeats 3 \
    --timeout 90 --out stock.json
```

## What these numbers are not

- **One host, one graph shape.** A different graph moves individual rows. The
  path queries win by margins too large for shape to reverse; the millisecond
  prebuilts could go either way.
- **p50, not tail latency.** The harness reports the median of three runs.
- **Read-only.** BloodTrail writes through to PostgreSQL and maintains its
  in-memory replica on top, so ingest is slower than stock. That trade is
  deliberate: BloodHound is written to rarely and read from constantly.
- **Memory is the cost.** BloodTrail held 1.92 GiB resident against stock's
  1.21 GiB on this run, and the gap is wider on a quiet instance -- the stock
  arm's figure includes PostgreSQL's own page cache warmed by the sweep.
